# Rust → Swift FFI spike

A throwaway proof-of-toolchain: one trivial DSP function, exposed two ways
(UniFFI copy vs raw C-ABI zero-copy), packaged as an `.xcframework` and
consumed from a standalone Swift package. **Not wired into the ShoutKit app
target** - this directory is disposable and can be deleted without touching
`ShoutKitApp` or `Packages/`.

Goal: validate the whole Rust → staticlib → xcframework → SPM pipeline
end-to-end, and get a real number on whether the raw zero-copy path is worth
the extra shim versus just using UniFFI everywhere on the eventual render-thread
audio path.

## Layout

```
rust-spike/
  rust/                      Cargo lib crate (staticlib + cdylib)
    src/lib.rs               shared DSP core + both FFI variants + unit tests
    include/ShoutKitRustSpikeRaw.h   hand-written header for the raw C export
    uniffi-bindgen.rs         `cargo run --bin uniffi-bindgen` entry point
  build.sh                   Phases 2-3 automated: cross-build, lipo, bindgen, xcframework
  swift/
    Package.swift            SPM package: binaryTarget(xcframework) + wrapper targets
    Sources/RustSpike/        RawBridge.swift + Generated/ (bindgen output, regenerated by build.sh)
    Tests/RustSpikeTests/     CorrectnessTests.swift, BenchmarkTests.swift
    artifacts/                 build.sh drops the .xcframework here (gitignored)
```

## ⚠️ Execution environment for this spike

This was implemented in a **Linux container with no Xcode, no Swift toolchain,
and no iOS SDKs** - only `rustc`/`cargo`/`rustup`. That is a hard blocker for
Phases 3-5, which require `xcodebuild` and an iOS simulator/device. Below is
an honest per-phase account of what was actually executed here vs. what is
written-but-unverified and needs a Mac to confirm.

| Phase | What it covers | Status in this environment |
|---|---|---|
| 1 | Rust crate, two variants, unit tests | ✅ **Built and tested natively** (`cargo test`, 9/9 passing) |
| 2 | UniFFI bridge, Swift bindings/header codegen | ✅ **Bindings generated and inspected** via `uniffi-bindgen generate --library <host cdylib>` - this step is host-independent codegen, so it ran for real on Linux. Also **empirically confirmed** the `aarch64-apple-ios` **staticlib** cross-compiles and links (`.a` produced) without Xcode; only the `cdylib` link step for that target failed, because *that* needs `xcrun`/an Apple SDK, which only Xcode provides |
| 3 | XCFramework packaging (`build.sh`) | ⚠️ **Script written, not executed** - `xcodebuild -create-xcframework` doesn't exist on this host. The modulemap-injection logic inside `build.sh` (the part I could isolate from Xcode) was verified against the real generated modulemap and produces correct output |
| 4 | SPM package + correctness tests | ⚠️ **Code written, not executed** - no Swift compiler here. Logic mirrors the passing Rust unit tests (same known input, same tolerance, cross-checked against both variants) |
| 5 | Benchmark (copy vs zero-copy) | ⚠️ **Code written, not run.** No fabricated numbers below - see "Benchmark results" |

**Before trusting this spike, someone needs to run `./build.sh` and
`xcodebuild test` on an actual Mac with Xcode 26** and confirm Phases 3-5.
Everything up to that boundary is real, executed evidence, not assumption.

## Rebuild commands (run on macOS with Xcode + rustup)

```sh
# One-time
rustup target add aarch64-apple-ios aarch64-apple-ios-sim x86_64-apple-ios-sim

# Phase 1 - Rust unit tests (host target)
cd rust-spike/rust
cargo test

# Phases 2+3 - cross-build, lipo, bindgen, xcframework (single script)
cd rust-spike
./build.sh
# prints the resulting .xcframework path at the end

# Phase 4 - correctness tests on an iOS simulator
cd swift
xcodebuild test -scheme RustSpike -destination 'platform=iOS Simulator,name=iPhone 16'

# Phase 5 - benchmark (Release, ideally on a physical device)
xcodebuild test \
  -scheme RustSpike \
  -configuration Release \
  -destination 'platform=iOS,name=<your device name>' \
  -only-testing:RustSpikeTests/BenchmarkTests
# console output includes the per-size ns/call table; check the printed
# "destination:" line to confirm it actually ran on device vs simulator
```

`swift test` (plain SPM) also works for Phase 4/5 once `build.sh` has dropped
the xcframework into `swift/artifacts/`, but only against the simulator SDK
that matches your host arch - use `xcodebuild test` with an explicit
destination for a real device run.

## Takeaway (provisional, pending on-device numbers)

Based on how the two paths are built - not measured - here's the expected
shape of the result: `normalize_gain` marshals the sample buffer into a
`RustBuffer` (allocate + copy on the way in, versus `normalize_gain_raw`
which is just a pointer + length passed straight through with zero
allocation. For a 256-4096 `f32` sample buffer (1-16 KB) called once per audio
buffer at typical render rates, that copy is unlikely to matter as raw
wall-clock, but it is extra allocator pressure on a render thread where
allocation-free operation is usually the actual constraint (not raw
throughput). **Recommendation once confirmed on device**: if the measured
delta is small in absolute ns and the render thread already tolerates
UniFFI's allocation elsewhere, prefer the UniFFI path everywhere for
simplicity; reach for the raw zero-copy shim specifically for the
audio-callback-adjacent hot path where the allocation itself (not just the
time) is the thing you're avoiding. Do not adopt this recommendation without
running Phase 5 for real - this paragraph is a hypothesis, not a result.
